# Reverse egress: домашний узел как выход

Узел за NAT (домашний компьютер, роутер) **сам подключается к ingress** и становится выходом для потоков клиентов
этого ingress. Трафик клиента выходит в интернет с домашнего адреса, хотя входящих соединений на дом никто не открывает.

> Описано по коду `core/src/net/connection/{reverse_egress,handler,connection}.rs` и тестам
> (`cargo test -p netrunner-core --lib reverse_egress`, а также `connection::tests`: `reverse_egress_carries…`, `require_mode…`, `exit_policy…`, `egress_flow_limit…`).
> Не проверено на двух реальных хостах — только loopback.

## Как устроено

* **Кто кого набирает, не определяет, кто открывает цели.** Роль данных задаётся `StreamHandler::opener`: у набравшего
  (`ClientHandler::connect_egress`) он есть — он открывает цели; у принявшего (ingress) его для такой сессии нет, и ingress
  открывает потоки *к набравшему* через `MeshPeerSession` — тем же способом, что и mesh-хопы (`bridge_via_peer`).
* **Токен набравшего:** `egress:<метка>:<обычный клиентский токен>`. Метка информационная (имя выхода в реестре).
* **Ingress включает роль явно:** `ServerHandler::with_reverse_egress(Arc<ReverseEgressRegistry>)`. Без реестра ingress
  такую роль не предлагает вообще — токен `egress:…` отклоняется (раньше он считался обычным токеном).
* **Права:** `AuthValidator::validate_egress` (по умолчанию — отказ). Обычный клиентский токен выход не даёт: иначе любой
  клиент мог бы объявить себя выходом и получать чужой трафик. Без `require_auth` роль не выдаётся.
* **Куда идут потоки клиентов:** `ExitMode` реестра — `Local` (как раньше, по умолчанию), `Prefer` (через выход, нет —
  локально), `Require` (только через выход; нет выхода — поток закрывается, **никогда** не выходит с ingress).
  `ExitPolicy::choice_for(user_id)` решает по клиенту: `Default` (по режиму), `Local`, `Egress(метка)` (только через этот
  выход; метки нет — отказ, без отката на ingress).
* **Безопасность выхода:** `EgressPolicy` на стороне набравшего. По умолчанию цели loopback/private/link-local/CGNAT/metadata
  отклоняются, адрес проверяется ровно тот, к которому идёт соединение (повторного резолва нет — подмена DNS не работает);
  `allow_private` включает LAN дома. `max_streams` ограничивает число одновременных потоков (лишние получают `Close`).
* **Только TCP.** UDP-потоки клиентов при удалённом выходе закрываются (не уходят локально втихую); у набравшего нет
  datagram-ноги.

## Что меняется для обычных клиентов и серверов

Ничего на проводе: новых кадров нет, формат хендшейка тот же. Сервер без реестра ведёт себя как раньше, кроме отказа на
`egress:`-токены. Старый клиент работает с новым сервером и наоборот (проверено, см. коммит).

## Доставка Connect (сопутствующее исправление)

Раньше `Connect` (и его варианты) шёл по управляющей очереди ноги через `try_send`: при переполнении очереди (16 слотов)
кадр молча пропадал — без повтора и без подтверждения, локальный сокет зависал навсегда. Браузер, открывающий десятки
соединений сразу, натыкался на это постоянно. Теперь Connect — критичный кадр (как `Close`/`Heartbeat`/`Credit`): отправка
`send().await`, блокируется только задача этого потока.

## Коннектор организации (`netrunner-connector`)

Тот же механизм, но для сервисов во внутренней сети клиента: бинарь `netrunner-connector` (`server/src/bin/`) стоит рядом с
ними, сам набирает ноду организации и открывает потоки изнутри (`allow_private` включён намеренно). Входящих портов не нужно.

* **Нода** запускается с `--connectors` (требует `--require-auth`): создаёт `ReverseEgressRegistry` в режиме `Local` — сам по
  себе трафик через коннекторы не идёт.
* **Что идёт через коннектор** решает политика доступа пользователя (`net::access_policy`, приходит в ответе на проверку
  токена): у правила ресурса поле `via` = метка коннектора. Поток к такому ресурсу открывается **только** через него; нет
  коннектора с этой меткой — поток закрывается, на прямой выход с ноды он не откатывается. UDP к такому ресурсу закрывается
  (коннектор переносит только TCP).
* **Токен коннектора** проверяет бэкенд (`AuthValidator::validate_egress` → `/internal/validate-connector`). Метку выхода
  назначает валидатор (`UserQuota::exit_label`), а не набравший: иначе владелец одного коннектора мог бы назваться чужим
  и перехватывать его потоки.

## Политика доступа на ноде (`net::access_policy`)

Для сотрудников организации бэкенд возвращает `access_policy` (`default_deny`, `allow[]`, `deny[]`); нода применяет её к
каждому новому потоку в `RemoteOpener::open_{tcp,udp}_with_privacy`. Запрет сильнее разрешения и действует по адресу
(«широкая подсеть минус боевой контур»); имя назначения проверяется и по имени, и по адресам, в которые резолвится;
нераспознанное правило закрывает политику целиком. Без поля `access_policy` поведение прежнее. Ограничение: имя
резолвится для проверки и ещё раз при подключении.
